- **작성 근거**: 지적받은 항목을 **전부 소스코드에서 직접 확인**했습니다. 아래 주장에는 근거 위치를 답니다.

## 0. 요약

지적해 주신 **현상은 대부분 사실이었습니다.** 총액 불일치도, 경고 등급 문제도 실재합니다.
다만 **원인 진단이 5건에서 빗나갔고**, 그 결과 제시하신 처방 중 일부는 이미 적용되어 있거나
적용해도 효과가 없는 것이었습니다.

가장 중요한 하나: **수치 불일치는 LLM 환각이 아닙니다.** 요청 모델에 환율 필드가 선언되지
않아 프런트가 보낸 실시간 환율이 조용히 버려지고 있었습니다. LLM은 주어진 값을 정확히
인용했습니다. 이미 고쳤고 회귀 테스트를 붙였습니다.

| 구분 | 건수 |

| 사실이며 이미 고침 | 4 |
| 사실이며 고칠 예정(오너 판단 대기) | 6 |
| 현상은 맞으나 **원인 진단이 틀림** | 5 |
| 보안·비용 때문에 반대 | 4 |

## 1. 반박 — 원인 진단이 빗나간 5건

### R1. "LLM이 임의로 반올림·재계산했다" → 환율 필드 누락입니다

**지적(Gemini)**: "LLM이 임의로 반올림/재계산을 수행한 것으로 보입니다. LLM 프롬프트에
'제공된 수치를 절대 재계산하지 말고 그대로 인용할 것'이라는 시스템 지시어를 추가해야 합니다."

**사실**: 그 지시어는 **이미 있었고, 지금도 있습니다.** 그것도 가장 강한 형태로:

```
[절대 규칙 — 수치 정합성 (위반 시 리포트 무효)]
1. 본문에 등장하는 모든 수치(비중%, 평가액, 수익률%)는 ... 제시된 값만 **그대로 인용**하라.
   제시되지 않은 숫자를 추정·생성하지 마라(환각 금지).
2. 총 평가 자산은 반드시 ₩{total_krw}만 사용하라. 다른 총액을 쓰지 마라.
```

**진짜 원인은 세 줄로 설명됩니다.**

1. 프런트는 전략 분석 호출에 실시간 환율을 **보내지 않았습니다**. 같은 화면의
   health·alerts·dividends 호출에는 `usd_krw: usdKrw` 가 들어 있습니다.
2. 설령 보냈어도 **버려졌습니다.** `StrategyReq` 모델에 `usd_krw` 필드가 없었습니다.
   Pydantic은 선언되지 않은 필드를 **에러 없이 폐기**합니다.
3. 그래서 전략 계산만 `usd_krw = 1380.0` 상수를 썼습니다.

**이 가설은 숫자로 검증됩니다.** 보고해 주신 미국 계좌 두 값의 비율:

```
392,894,929 / 379,506,281 = 1.0353
1380 / 1.0353 = 1332.9
```

즉 **그 시점 실제 환율이 약 ₩1,333이었다면 모든 수치가 정확히 설명됩니다.**
총액 차이(+1.87%)가 미국 계좌 차이(+3.53%)보다 작은 것도 같은 이유입니다 —
한국 자산은 환율과 무관하므로 희석됩니다.

NVDA 평가액 차이(₩144,432,682 → ₩149,040,000, +3.19%)도 같은 범위입니다.
**LLM은 두 숫자 중 어느 쪽도 만들지 않았습니다.** 백엔드가 1380으로 계산해 건넨 값을
그대로 인용했을 뿐입니다.

> **처방이 효과가 없는 이유**: 프롬프트를 아무리 강하게 써도, 모델을 바꿔도 고쳐지지
> 않습니다. LLM이 계산하는 자리가 아니기 때문입니다.

**조치(완료)**: `StrategyReq.usd_krw` 추가 · `_effective_usd_krw()` 로 우선순위 고정
(요청값 → 서버 조회 → 상수) · 회귀 테스트 7개. 상수는 이제 **폴백이지 기본값이 아닙니다.**

### R2. "Claude Haiku는 복잡한 맥락 유지에 취약" → 실제 모델은 claude-sonnet-5입니다

**지적(Gemini)**: "Claude Haiku 모델은 속도가 빠르지만 복잡한 맥락 유지에 취약할 수 있습니다."

**사실**: 전략 리포트는 `MODEL_ANALYSIS = "claude-sonnet-5"` 로 호출됩니다. Haiku는 원칙
요약 같은 가벼운 작업용 별도 상수입니다.

**다만 이것은 검증자의 잘못이 아니라 저희 문서의 결함이었습니다.** 내보내기 문서가
5번 섹션 제목을 `## 5. AI 전략 리포트 (Claude Haiku)` 로 **손으로 적어 두었고, 그 라벨이
틀린 채 굳어 있었습니다.** 문서대로 읽으신 것이 맞습니다.

**조치(완료)**: 제목의 모델명 하드코딩 제거 → 서버가 준 `model` 값을 씁니다.
값이 없으면 **적지 않습니다** — 틀린 라벨보다 공백이 낫습니다.

→ 모델 업그레이드 권고는 전제가 무효화되었습니다. 재평가를 요청드립니다(Q2).

### R3. "discovery_horizon 종목 추천은 LLM의 논리적 모순" → LLM 출력이 아닙니다

**지적(Gemini)**: "discovery_horizon에서 은퇴 임박 시 고위험 혁신주를 0%로 줄이라고
명시해놓고, 단기/중기 추천 종목으로 Ginkgo Bio, Absci, Relay Tx 같은 초고위험 기업을
추천했습니다. (Hallucination)"

**사실**: `discovery_horizon` 은 **LLM이 생성하지 않습니다.** 백엔드가 계산한 값으로
LLM 출력을 **덮어씁니다**:

```python
result['discovery_horizon'] = discovery_horizon   # _run_strategy_job
```

후보는 `_discovery_candidates_by_horizon()` 가 결정론적으로 뽑습니다.
프롬프트에는 이미 `저점발굴 종목은 투기적이므로 절대 핵심(core) 자산으로 다루지 마라` 가
들어 있습니다.

**모순 자체는 실재합니다.** 다만 원인은 후보 풀이 사용자 프로필(은퇴 시점·위험 성향)과
연동되지 않는 것이며, **프롬프트·모델을 고쳐도 해결되지 않습니다.** 필터를 고쳐야 합니다(T6).

### R4. "RAG 과정에서 외부 배당 템플릿이 사용자 데이터를 덮어쓴 과적합 오류"

**지적(Gemini)**: 보유하지 않은 JEPI·SCHD·O·맥쿼리인프라로 배당 시뮬레이션을 돌린 것은
"RAG(검색 증강 생성) 과정에서 외부 배당 템플릿이 사용자 데이터를 덮어쓴 전형적인 과적합 오류".

**사실**: **이 앱은 RAG를 쓰지 않습니다.** 검색 증강도, 외부 템플릿도, 벡터 DB도 없습니다.
프롬프트가 **명시적으로 추천을 요구**합니다:

```json
"dividend_simulation": {
  "rows": [{"account": "계좌", "asset": "추천 배당자산(ETF/리츠)", "weight": 30, "monthly_cashflow": "..."}]
}
```

즉 **스펙대로 동작했습니다.** 보유 자산으로 시뮬레이션하라고 요구한 적이 없습니다.

**그러나 지적하신 문제는 실재합니다** — 출력에 '보유'와 '추천'이 구분 없이 나란히 보여
읽는 사람이 보유로 오해합니다. Perplexity의 "현재 보유 기준과 가상 재배분안을 분리"가
정확한 처방입니다. 수용합니다(T5).

추가로 저희가 더 심각하다고 보는 것: `total_monthly`(₩2,730,000)를 **LLM이 계산**합니다.
"수치를 지어내지 마라"는 규칙과 "월 현금흐름을 계산하라"는 요구가 **같은 프롬프트 안에서
충돌**합니다. 파이썬 연산으로 옮깁니다.

### R5. "경고가 사용자 결정을 모호하게 되돌린다" → 의도된 안전장치입니다

**지적(Perplexity)**: "'손절/추가매수/관망 중 점검'을 반복합니다. 이는 사용자가 결정해야 할
사항을 모호하게 되돌리는 출력입니다."

**사실**: 단정적 투자 지시를 **금지하는 규칙이 프롬프트에 명시**되어 있습니다:

```
금지 예: "줄여라", "매도하라", "확인할 것", "비중 과다임", "조정 필요".
```

개인 투자 도구가 확정적 매매 지시를 내는 것을 피하기 위한 설계입니다. 모호함은 버그가
아니라 **의도**입니다.

**다만** Perplexity의 "실행 명령이 아닌 **시나리오**로 출력하라"는 그 의도를 더 잘 구현하는
방법입니다. '모호하게 되돌리기' 대신 '선택지와 각각의 근거'를 주는 쪽으로 수용합니다(T5).

| # | 내용 | 조치 |
|---|---|---|
| F1 | 전략 계산이 환율 상수 1380 사용 | `StrategyReq.usd_krw` 추가 + `_effective_usd_krw()` 우선순위 + 테스트 7개 |
| F2 | 무엇으로 계산했는지 알 수 없었음 | `verified_facts` 에 `usd_krw`·`computed_at` 동봉 |
| F3 | 문서의 모델명이 틀린 채 고정 | 서버가 준 실제 모델명 사용, 없으면 표기 안 함 |
| F4 | **5번 리포트는 캐시된 과거 결과일 수 있는데 생성 시각이 문서에서 제거되고 있었음** | 생성 시각 명시 + "1~4번은 지금, 5번은 생성 시점" 경고 추가 |

**F4가 이번 검증 혼란의 숨은 절반입니다.** 내보내기 함수가 `computed_at`·`model` 을
`skip` 목록에 넣어 **의도적으로 버리고 있었습니다.** 그래서 두 분 모두 며칠 전 리포트와
오늘 시세를 같은 시점으로 보고 비교하실 수밖에 없었습니다. 문서가 정보를 숨긴 것입니다.

## 3. 수용 — 고칠 것 (오너 판단 대기, 6건)

### T1. 경고 등급에 비중을 반영 (Gemini 지적 — 코드로 확인됨)

현재 코드는 **손실률만** 봅니다:

```python
severity = 'critical' if e['pnl_pct'] <= max_loss * 1.5 else 'med'
```

비중 0.1% 종목의 -64%와 비중 24% 종목의 -20%가 같은 등급이 됩니다. 사실입니다.

**다만 "필터링해서 빼라"는 제안에는 반만 동의합니다.** 비중 0.1%의 -69%는 포트폴리오
타격은 없지만 **판단 오류의 신호**로서는 가치가 있습니다. 숨기면 같은 실수를 반복합니다.
→ **제거가 아니라 등급 분리**: `영향도 = 비중% × 손실률%` 를 등급에, 손실률은 목록에 유지.

### T2. Health Score 실패 시 하위 진단 강등 (Perplexity)

Score가 "계산 실패"인데 그 아래 샤프·MDD 기반 진단은 확신에 차서 나옵니다. 강등 규칙 추가.

### T3. HHI · 유효 종목 수 (Perplexity)

계산이 간단하고 즉시 가치가 있습니다. `HHI = Σwᵢ²`, 유효 종목 수 = `1/HHI`.

### T4. 실질 환노출 — **계좌가 아니라 자산 통화 기준** (Gemini)

타당합니다. 퇴직연금의 TIGER 미국나스닥100은 원화로 사지만 환노출 상품입니다.
계좌 기준 64.4%가 아니라 **자산 기준**으로 다시 집계해야 합니다. 계산 비용 거의 없음.

### T5. 배당 시뮬레이션 — 보유/추천 분리 + 금액은 파이썬 계산

R4 참조. 라벨 분리 + `total_monthly` 를 결정론적 계산으로.

### T6. 저점발굴 후보를 사용자 프로필로 필터

R3 참조. 은퇴 시점·위험 성향을 `_discovery_candidates_by_horizon()` 에 전달.

## 4. 반대 또는 주의 — 보안·비용·UI (4건 + 1)

### X1. 다중 LLM 앙상블(심사관 2~3개) — **반대**

Perplexity가 제안한 "서로 다른 계열의 LLM 2~3개가 심사, 다수결" 구조는 품질 면에서는
합리적이지만 이 앱에는 **두 가지 이유로 맞지 않습니다.**

1. **보안**: 입력이 개인 금융정보 전량(보유 종목·수량·평가액·손익)입니다. 심사 모델을
   늘린다는 것은 **같은 데이터를 외부 벤더 2~3곳에 더 보낸다**는 뜻입니다. 모델 품질
   이득보다 유출면 확대가 큽니다.
2. **비용**: 이 앱은 2026-10-18에 중복 cron 하나를 끄며 API 비용을 월 $10 → $2로
   줄인 참입니다. 앙상블은 호출당 비용을 3~5배로 만듭니다.

→ **대안**: 심사는 **규칙 기반 검증기**로 합니다. 지적하신 자동 실격 조건 대부분은
LLM 없이 코드로 판정됩니다 — 수치가 입력과 다른가, 보유하지 않은 자산을 보유처럼
서술했는가, 금지어를 썼는가. 외부 LLM 교차검증은 **지금처럼 가끔 수동으로** 돌립니다.

### X2. `portfolio_state.json` 을 파일로 떨구기 — 조건부 수용

단일 진실 원천이라는 **원칙은 전적으로 동의하며 이미 그 방향으로 고쳤습니다**(F1·F2).
다만 **파일로 디스크에 쓰는 것은 반대**합니다 — 개인 금융정보가 담긴 파일이 하나 더
생기고, 그것은 또 하나의 유출 경로입니다. 요청-응답 사이의 메모리 객체로 충분합니다.

### X3. 리포트 5단 구조로 전면 재편 — 보류

제안하신 구조(스냅샷 → 확인된 리스크 → 해석 → 선택지 → 확인 필요)는 좋습니다.
다만 분석 탭은 2026-10-11에 Ⅰ.현황 / Ⅱ.진단 / Ⅲ.제안 으로 이미 재편했고, 실사용
2주 만에 또 바꾸면 사용자가 익힌 위치가 다시 흔들립니다.
→ **화면 구조는 유지하고, 내보내기 문서에만** 적용하는 단계적 접근을 제안합니다.

### X4. 5개 버전 A/B 평가 — 비용 대비 보류

방법론은 표준적이고 타당합니다. 다만 사용자 1명 규모에서 버전 5개 × 반복 실행은
API 비용이 수 배가 됩니다. **T1~T6을 먼저 적용하고, 정답형 평가(비중 합계·HHI·계좌별
합계처럼 정답이 계산 가능한 항목)만** 자동화하는 편이 비용 대비 효과가 큽니다.

### X5. 가장 큰 보안 리스크는 이 문서 자체입니다

내보내기 md에는 **보유 종목·수량·평가액·손익이 전부** 들어 있습니다. 현재 경고 문구는
한 줄뿐입니다(`본 문서는 개인 보유 데이터를 포함합니다`). 외부 LLM에 반복해서
붙여넣으면 그 데이터는 여러 벤더에 누적됩니다.

→ **익명화 내보내기 옵션**을 제안합니다: 금액을 전부 제거하고 **비중(%)과 손익률(%)만**
남기면, 이번에 지적된 분석 대부분(집중도·HHI·섹터 쏠림·경고 등급)은 그대로 가능합니다.
절대 금액이 필요한 분석은 절세 시뮬레이션뿐입니다.
