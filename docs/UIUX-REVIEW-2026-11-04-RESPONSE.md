## 0. 가장 중요한 한 가지 — 세 곳이 **같이 틀렸다**

세 보고서 모두 1순위/P0로 같은 것을 짚었다.

> "결측 축의 가중치를 재정규화만 하면, 데이터가 없는 종목의 점수가 부풀려진다."

**사실이 아니다.** 재정규화 **위에** 결측 감점이 이미 걸려 있다.

`backend/main.py:4363`
```python
base = num / den if den > 0 else 0.0          # 가용 축만 재정규화
r['composite_score'] = round(base * (r['data_completeness'] / 5.0), 2)   # ← 결측 감점
```

4/5축 종목은 **×0.8**, 3/5축은 **×0.6**이 이미 적용된 값이 화면에 뜬다.
(3축 미만은 `data_completeness < 3` 에서 아예 탈락한다 — `main.py:4348`.)

### 세 처방을 실제 숫자로 대입해 봤다 (삼성전자, 4/5축, 현행 68.3)

현행 68.3 = base 85.4 × 0.8 이므로, 가용 4축 가중합 Σ(w·s) = 55.5.

| 처방 | 계산 | 결과 | 현행 대비 |
|---|---|---:|---|
| **현행** | 85.4 × (4/5) | **68.3** | — |
| Gemini: 결측축에 50점 대입 + 분모 1.0 고정 | 55.5 + 0.35×50 | 73.0 | **+4.7 더 후함** |
| Perplexity: `raw×conf + median×(1−conf)` | 85.4×0.8 + 50×0.2 | 78.3 | **+10.0 더 후함** |
| Perplexity가 "지나치게 불리하다"며 **기각한** 대안 `raw×conf` | 85.4 × 0.8 | 68.3 | **= 지금 쓰는 식** |

세 보고서가 "점수가 부풀려진다"며 내놓은 처방이, 전부 **지금보다 점수를 올리는** 처방이다.
특히 Perplexity가 "너무 가혹해서 권장하지 않는다"고 적은 식이 이미 돌아가고 있는 바로 그 식이다.

처방끼리도 충돌한다 — Gemini의 1위 제안(결측축에 중립값 대입)을 ChatGPT는 권고안 C에서 **명시적으로 반대**한다("임의의 0점이나 평균값을 넣는 방식은 권장하지 않는다").

### 그래도 이건 **우리 잘못**이다

세 곳이 똑같이 틀렸다면 원인은 읽는 쪽이 아니라 **쓴 쪽**이다.
`UIUX-REVIEW-REQUEST.md` 와 발굴 MD 어디에도 `× 완성도/5` 가 적혀 있지 않았다. 화면에도 "완성도(n/5)"라는 말만 있었지 **몇 배 깎였는지**가 없었다.

→ **수용(설명 방식).** 상세 화면에 수치로 못 박았다:
> 이 종목은 **1개 축이 비어** 점수에 **×0.8** 감점이 이미 적용된 값입니다.

## 2. 반박한 것

### 2-1. "섹터 상한을 걸어라" — 거부
- Gemini: 한 섹터 최대 30%(15종 중 4종) 강제 / Perplexity: 섹터당 2~3개
- **거부 이유**: 점수가 높은 종목을 쿼터로 잘라내면 **왜 안 보이는지 알 수 없다.** 이 앱이 하지 않기로 한 '대신 판정하기'다. ChatGPT도 같은 이유로 상한 대신 공시를 권했다("업종별 종목 수를 강제로 제한하면 실제로 좋은 기회를 숨길 수 있다").
- **대신**: 사실만 띄운다(§1-E). 걸러내는 건 이미 있는 섹터 필터로 오너가.

### 2-2. "레이더는 축 순서에 따라 면적이 왜곡된다" — 이 앱엔 해당 없음
- Gemini의 일반론은 맞다. 다만 다온의 축 순서는 `AXES` 상수로 **고정**이라 종목 간 비교에서 면적 왜곡이 생기지 않는다. 바뀌는 건 점수뿐이다.

### 2-3. "결측 축이 0으로 찍혀 '최악'으로 오인된다" — 틀림
- `<Radar connectNulls />` 라 결측 축은 **그리지 않고 건너뛴다.** 0으로 내려 찍히지 않는다. (`DiscoverTab.jsx` 레이더 블록)
- 다만 "결측인지 알기 어렵다"는 지적 자체는 맞아서 §1-C로 수용.

### 2-4. 보고서 자체의 사실 오류
- Gemini: "에너지 섹터가 **7종**(PSX, EOG, VLO, CVX, MPC, XOM, COP, OXY 포함 시 8종)" — 괄호 안에 8개를 나열하면서 7종이라 적었다.
- ChatGPT: "에너지 관련 기업은 다음 **6개**다" 라고 쓴 뒤 8개를 나열하고 "정확히 세면 **8개**"로 스스로 정정했다.
- Perplexity: `[file:17]`, `[file:18]` 인용 마커가 우리 문서에 없는 식별자다 — 근거 추적 불가.
- 숫자를 세는 일은 사람보다 코드가 낫다. 그래서 §1-E를 **사람이 세지 않게** 화면이 세도록 만들었다.

### 2-5. "11px 미만 269곳을 1단계로 일괄 통합" — 부분 거부
- Gemini 1단계 제안. 하지만 우리 실측 결과는 "안전"이 아니라 **"360px 기준 넘침 +6"** 이었다. 통과가 아니라 비용이다.
- 843곳 중 269곳을 한 번에 바꾸면 회귀 검사 범위(현재 브라우저 검사기 11종)를 넘는다.
- ChatGPT·Perplexity의 **점진 이전**안을 채택 — 토큰 먼저 정의, 신규 화면부터 강제, 반복 컴포넌트 순. 백로그 §3.

## 4. 오너 지적 — 상세 화면의 빈 여백

### 원인
`DetailPanel` 첫 열에 `maxWidth: 220` 이 걸려 있었다. 두 열이 줄바꿈되면 이 열만 220px로 남고 나머지가 **통째로 빈다.**

### 배포 전 운영에서 실측 (재현됨)
```
390px   패널 348px, 점수 열 220px  → 오른쪽 128px (37%) 빔
700px   패널 438px, 점수 열 220px  → 오른쪽 218px (50%) 빔
1000px  패널 806px, 점수 열 220px  → 2열로 들어가 여백 없음
```
오너 캡처는 **줄바꿈된 폭**에서 찍힌 것이었다.

### 배포 후 (같은 검사기)
```
  OK  390px  (줄바꿈) — 점수 열 336px / 패널 348px
  OK  700px  (줄바꿈) — 점수 열 426px / 패널 438px
  OK  1000px (2열)   — 점수 열 430px / 패널 806px
  OK  1440px (2열)   — 점수 열 434px / 패널 814px
```

### 왜 기존 검사기가 못 잡았나
`check-app-mode-wide.mjs` 는 **가로 넘침**만 본다. 여백은 넘치지 않는다 — 그래서 통과시켰다.
**넘침만 보는 검사기는 "남는 것"을 못 본다.** 반대쪽(열이 폭을 다 쓰는가)을 재는 검사기를 새로 만들었다.
→ `frontend/scripts/check-discover-detail.mjs`, `npm run check:discover`

## 5. 다음 검증에 내보낼 때 고칠 것

이번 오해(§0)는 **요청서가 산출 조건을 다 싣지 않아서** 생겼다. 다음부터는 교차검증 패킷에 아래를 반드시 포함한다.

1. `composite_score` 의 **실제 코드 한 줄** (말로 풀어 쓰지 말고 식 그대로)
2. 탈락 규칙 전부 (`data_completeness < 3`, `current_price is None`, GARP 게이트)
3. 각 축에 들어가는 **원천 지표 목록** — 세 보고서 모두 "축별 정의서가 없어 판정 불가"라고 적었다. 이건 정당한 지적이다
4. 목표가의 출처·최소 애널리스트 수
5. 모집단 정의(US/KR 각각 몇 종에서 백분위를 냈는지)
