## 0. 먼저: 이 앱이 실제로 지키는 것

방법론을 고르기 전에 **무엇을 잃을 수 있는지**부터 확정해야 한다. 점검의 우선순위는 전부
여기서 나온다.

| 자산 | 어디에 있나 | 잃으면 |
|---|---|---|
| 개인 금융 데이터 (평가액·보유 종목·거래내역) | `daon.db` (SQLite, 600) | **복구 불가.** 자산 규모·포지션이 곧 사회공학 공격의 재료 |
| 세션 토큰 | `secrets.token_hex(32)` = 256bit, DB 저장 | 계정 완전 탈취 |
| 비밀번호 | PBKDF2-HMAC-SHA256 100,000회 + 16B salt | 해시 유출 시 오프라인 크래킹 |
| Anthropic API 키 | `settings` 테이블 **평문** | 타인이 내 크레딧으로 무제한 호출 = 직접 금전 손실 |
| VAPID 개인키 | 서버 | 사용자에게 위조 푸시 발송 (피싱 벡터) |
| `cron_secret` | `settings`, `secrets.token_hex(24)` | 배치 임의 실행 → AI 비용 유발 |
| Oracle 서버 SSH 키 | **오너 PC** `~/Downloads/oracle-key.key` | 서버 전체 장악 |
| 데모 공개 체험 | 인증 없이 접근 가능한 경로 | 미인증 사용자에게 열린 유일한 표면 |

**핵심 비대칭**: 사용자 1명(오너)뿐인 앱이라 "대규모 유출"은 없다. 대신 **단일 계정 탈취 =
전부 상실**이다. 다중 사용자 서비스의 표준 위협모델을 그대로 가져오면 과잉이고,
계정 탈취·서버 장악·비용 유발 세 축에 집중하는 게 맞다.

## 1. 검증 방식 비교 — 3자 vs 자체

### 1-A. 자체 검증 (self-assessment)

| 방식 | 비용 | 잡는 것 | 못 잡는 것 |
|---|---|---|---|
| **정적 분석** (`bandit`, `semgrep`, `pip-audit`, `npm audit`) | 무료·CI 상시 | 알려진 취약 패턴, 취약 의존성 버전 | 비즈니스 로직 결함(권한 경계), 설계 오류 |
| **AI 코드리뷰** (`/security-review`) | 세션 비용 | 변경분의 주입·인증우회·데이터노출 | 런타임 설정, 실제 익스플로잇 가능성 |
| **수동 위협모델링** | 시간만 | 설계 수준 결함, 권한 경계 | 구현 디테일 누락 |
| **DAST** (ZAP 등 실행 중 스캔) | 무료·시간 | 헤더 누락, 인증 우회, 노출 엔드포인트 | 인증 뒤 깊은 로직 |

**장점**: 비용 0에 가깝고, **반복 가능**하다. 코드가 바뀔 때마다 돌릴 수 있는 게
가장 큰 가치 — 1회성 감사보다 상시 검증이 실제 위험을 더 줄인다.
**한계**: 자기 코드의 가정을 자기가 의심하기 어렵다. "여긴 내부만 부르니까 괜찮다"는
바로 그 가정이 뚫리는 지점이다.

### 1-B. 3자 검증 (third-party)

| 방식 | 대략 비용 | 적합성 |
|---|---|---|
| **전문 침투테스트 업체** | 수백만~수천만원 | 개인 프로젝트엔 **과잉**. 규제·고객 요구가 있을 때 |
| **버그바운티** (HackerOne 등) | 운영부담 + 포상금 | 공개 서비스·사용자 규모 필요. 현재 부적합 |
| **자동 SaaS 스캐너** (Snyk, Semgrep Cloud, Dependabot) | 개인 무료 티어 존재 | **현재 가장 합리적인 3자 요소** |
| **동료 개발자 리뷰** | 무료 | 편향 제거 효과가 비용 대비 가장 큼 |
| **Cloudflare WAF** (이미 사용 중) | 이미 지불 | 자동화 공격·스캐너 1차 차단. 이미 3자 방어층 |

**장점**: 자기 가정 밖에서 본다. 실제 익스플로잇까지 증명한다.
**한계**: 비용, 그리고 **스냅샷**이라는 점 — 감사 다음 주 커밋은 검증되지 않는다.

### 1-C. 권고 — 이 프로젝트에 맞는 조합

> **"자체 상시 + 3자 자동, 3자 수동은 안 함"**

1. **CI에 정적 분석 상시화** — `pip-audit` + `bandit` + `npm audit`.
   가장 싸고, "감사는 스냅샷"이라는 한계를 유일하게 메우는 수단.
2. **Dependabot / Snyk 무료 티어** — 의존성 CVE를 3자가 대신 추적. GitHub 복구된
   지금(2026-08-18) 바로 켤 수 있다.
3. **위험 변경에만 `/security-review`** — 인증·권한·외부입력을 건드린 커밋.
4. **전문 침투테스트는 하지 않는다** — 사용자 1명, 공개 노출은 데모뿐. 비용이 위험을
   초과한다. **다중 사용자로 열 때 재검토.**

## 2. 예상 점검 요소 — 현 시점 상태와 함께

`✅` 확인됨 · `⚠️` 미비 · `?` 미확인(서버 접속 필요)

### 2-1. 인증 · 세션
| 항목 | 상태 | 근거 |
|---|---|---|
| 비밀번호 해싱 | ⚠️ PBKDF2-SHA256 **100k회** | OWASP 현행 권고는 600k. 즉시 위험은 아니나 상향 여지 |
| 세션 토큰 엔트로피 | ✅ `token_hex(32)` = 256bit | 추측 불가 |
| 로그인 레이트리밋 | ⚠️ **없음** | 2026-06 권고 미이행. 온라인 무차별 대입 가능 |
| 관리자 2FA | ⚠️ **없음** | 동상 |
| 세션 만료 | ⚠️ **30일** 고정 (`time() + 30*86400`) | 검증 시 `expires < time()` 확인은 정상. 다만 재로그인 없이 30일 유효 = 토큰 유출 시 노출 창이 길다 |
| 세션 회전 | ⚠️ 없음 | 비밀번호 변경·권한 변경 시 기존 토큰 무효화 경로 미확인 |

### 2-2. 권한 경계
| 항목 | 상태 |
|---|---|
| 계좌 소유권 검증 | ✅ `_user_account_keys`로 타 계좌 쓰기 차단 |
| admin 전용 경로 | ✅ `require_admin` 의존성 분리 |
| 데모 사용자 격리 | ✅ `_is_demo` — 재분석 차단·일일 예산 상한 |
| cron 인증 | ✅ `cron_secret` 불일치·미설정 모두 403 (fail-closed) |

### 2-3. 입력 처리
| 항목 | 상태 |
|---|---|
| SQL | ✅ 전부 파라미터 바인딩 (문자열 결합 없음) |
| 티커 검증 | ✅ 형식 + 야후 실재 확인 (2026-08-17) |
| XSS | ✅ React 기본 이스케이프, `dangerouslySetInnerHTML` 미사용 |

## 3. RISK 발현 시 영향도

발생가능성 × 영향으로 정렬. **상단 3개가 실제 우선순위다.**

### 🔴 R1. 로그인 무차별 대입 → 계정 탈취
- **경로**: 레이트리밋 부재 + 2FA 부재. 데모로 로그인 폼 위치가 공개돼 있음.
- **영향**: 전 재산 포지션·거래내역 열람, 데이터 조작. **금융 프라이버시 완전 상실.**
- **완화 현황**: Cloudflare WAF가 조악한 자동화는 막지만, 느린 분산 시도는 통과한다.
- **조치**: IP+계정별 로그인 시도 제한(5회/15분) → 그 다음 admin 2FA(TOTP).
  **이번 5건 중 가장 비용 대비 효과가 큰 단일 조치.**

### 🔴 R2. Anthropic API 키 유출 → 직접 금전 손실
- **경로**: DB 파일 유출(백업 평문·서버 침해) → 키 평문 노출.
- **영향**: 타인이 내 크레딧 소진. 자동 갱신 배치까지 붙은 지금 **탐지가 늦어진다**
  (원래도 비용이 나가는 구조라 이상 사용이 묻힌다).
- **조치**: ① Anthropic 콘솔에 **월 사용 한도** 설정 — 유출돼도 손실 상한이 생김
  ② 백업 파일 암호화 ③ 주기적 키 회전.
- 참고: 저장 자체를 암호화해도 서버가 복호화 키를 쥐고 있어야 하므로 이득이 제한적이다.
  **한도 설정이 더 실효적이다.**

### 🟠 R3. SSH 키 탈취 → 서버 장악
- **경로**: 오너 PC 침해. 키가 `Downloads/`에 평문이면 즉시 사용 가능.
- **영향**: 서버 전체 = DB + 모든 시크릿. 최악 시나리오.
- **조치**: 패스프레이즈 설정 여부 확인 → 없으면 즉시 추가. `~/.ssh/`로 이동 + 권한 600.

### 🔴 R4. `cron_secret` 유출 → AI 비용 유발 *(노출 실측 확인됨)*
- **경로**: 시크릿이 스크립트/환경변수에 있음.
- **영향**: 배치 반복 호출로 과금. 오늘 추가한 갱신 배치는 `max_tickers` 상한이 있어
  1회 비용은 묶여 있으나 **호출 횟수 자체는 무제한**이다.
- **2026-08-18 배포 후 실측으로 확인됨**: `/api/cron/*` 는 **공개 인터넷에서 도달 가능**하다.
  잘못된 secret 으로 POST 시 **403**(존재하지 않는 경로는 404) — 즉 엔드포인트가 외부에
  노출돼 있고 secret 만이 유일한 방어선이다. 기존 4개 전부 동일
  (`check_alerts`·`weekly_rebalance`·`discover_scan`·`refresh_holdings_analysis`).
- **조치**: Cloudflare WAF 규칙 또는 리버스프록시에서 `/api/cron/*` 를 외부 차단.
  cron 은 서버 내부에서 `127.0.0.1:8501` 로 호출하므로 **막아도 동작에 지장 없다.**
  ⚠️ 403 응답 자체가 "여기 cron 이 있다"는 정보를 주므로, 차단 시 404 로 떨어지는 게 낫다.

### 🟡 R5. 데모 경로를 통한 정보 노출
- **영향**: 데모 데이터만 노출이면 실피해 낮음. 단, 실사용자 캐시와 공유되는 지점
  (`stock_v2` 분석 캐시는 티커 단위 공유)은 종목 분석 텍스트뿐 — 개인 데이터 아님.
- **조치**: 현행 유지. 데모 예산 상한이 이미 작동 중.

### 🟡 R6. 의존성 CVE
- **영향**: 라이브러리에 따라 RCE까지. 현재 **추적 체계 없음**이 문제.
- **조치**: Dependabot 활성화(1분 작업).

## 4. 실행 순서 권고

| 순서 | 조치 | 소요 | 줄이는 위험 |
|---|---|---|---|

3번부터가 개발 작업이다.

## 5. 이 문서의 한계

- **서버 실물 부분 점검**: `/api/cron/*` 외부 노출은 배포 후 실측으로 **확인 완료**(R4).
  열린 포트·systemd 권한·Cloudflare 헤더 설정은 아직 확인하지 못했다. `?` 표시 항목이 그것.
- **git 히스토리 시크릿 스캔 미실시**: `gitleaks detect` 를 별도로 돌려야 한다.
- **동적 점검 미실시**: 실행 중 앱에 대한 DAST는 하지 않았다.
- 코드 정적 분석과 이번 브랜치 변경분 리뷰(취약점 0건)에 근거한 문서다.
