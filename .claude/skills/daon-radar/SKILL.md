# 다온 레이더 — 주 1회 자가발전 루프

## 왜 있는가

2026-09-09, 지인 한 명이 다온을 처음 써보고 30분 만에 10가지를 지적했다.
전부 맞는 말이었고, **전부 내가 먼저 찾을 수 있었던 것**이었다.
티커 자동완성, 콤마, 화면 밖 배너, 잘린 이름 — 새로운 기술이 필요한 게 아니라
"처음 쓰는 사람의 눈"이 없었을 뿐이다.

그래서 루프는 두 짝이다. 하나만 하면 반쪽이다.

- **바깥** — 세상이 무엇을 알아냈는지 (논문·앱·서비스·기사)
- **안** — 우리 화면이 지금 어떤지 (첫사용 관점의 기계 점검)

바깥만 보면 남의 기능을 베끼는 목록이 쌓이고, 안만 보면 있는 것을 다듬기만 한다.

## 언제

매주 월요일. 서버 주간 갱신(`daon-weekly-refresh.sh`, 월 06:00 KST)과 같은 날에 둔다.
오너가 "레이더 돌려"라고 하면 요일과 무관하게 실행한다.

## 1단계 — 안쪽 점검 (먼저 한다)

바깥을 보기 전에 우리 상태를 안다. 순서가 중요하다 —
새 기능 아이디어를 먼저 보면 지금 깨진 것이 작아 보인다.

```
node scripts/ux-firstuse.mjs https://daonwealth.com --selftest
node scripts/privacy-scan.mjs
node scripts/answer-split-check.mjs
```

`--selftest` 결과에 🔴 가 하나라도 있으면 **그 주의 다른 작업보다 먼저 고친다.**
규칙이 죽은 검사기는 초록불을 켜면서 결함을 통과시킨다. 없느니만 못하다.

이어서 **첫사용자 시뮬레이션**을 한 가지 시나리오로 직접 걷는다. 매주 다른 것을 고른다.

- 가입 → 첫 종목 등록 → 포트폴리오에 뜨는가
- 계좌 2개로 같은 종목 → 평단·수량이 합쳐 보이는가
- 금액 가림을 켠 채 전 탭 순회 → 어디선가 뚫리는가
- 폰(390px)에서 한 손으로 → 닿지 않는 버튼이 있는가

시나리오는 "되는가"가 아니라 **"설명 없이 알 수 있는가"**로 본다.
기능이 있는데 못 찾는 것이 지인 피드백 10건 중 4건이었다.

## 2단계 — 바깥 조사 (4개 레인, 각 1~2건만)

레인마다 웹 검색 1~2회. **최근 12개월** 것만 본다. 그보다 오래된 것은
이미 알려졌거나 이미 반영됐다.

| 레인 | 무엇을 찾나 | 검색 예 |
|---|---|---|
| 논문 | 포트폴리오 구성·리스크·행동재무 | `portfolio construction retail investor 2026 paper`, `behavioral finance loss aversion dashboard study` |
| 앱 | 개인 자산관리 앱의 새 화면·상호작용 | `portfolio tracker app 2026 new feature`, 뱅크샐러드·토스증권·Sharesight·Snowball Analytics 릴리스 노트 |
| 서비스·API | 데이터 소스, 무료 한도, 대체재 | `free stock market data API 2026`, ETF 구성종목·배당 데이터 |
| 기사 | 개인투자자가 실제로 겪는 문제 | 국내 증권/핀테크 기사, 리테일 투자자 행태 조사 |

**논문은 초록만 읽고 넘기지 않는다.** 결론이 다온의 어떤 숫자를 바꾸는지
말할 수 없으면 그 논문은 이번 주에 필요 없는 것이다.

## 3단계 — 거르기 (여기가 진짜 일이다)

찾은 것 전부를 적지 않는다. **주당 채택 상한 3건.**
상한이 없으면 백로그는 늘고 앱은 그대로다.

각 후보에 세 줄을 쓴다. 한 줄이라도 못 쓰면 **기각**이다.

1. **무엇** — 한 문장. 출처 URL.
2. **다온의 무엇이 바뀌나** — 화면 이름 또는 함수 이름. "분석 탭의 집중도 진단",
   `_etf_top_holdings` 처럼 구체적으로. "전반적으로 좋아진다"는 기각 사유다.
3. **비용** — 토큰/API/작업량. 모르면 "모름"이라고 쓴다. 모른다고 쓰는 것은 통과다,
   모르는 걸 안다고 쓰는 것이 실패다.

**기각도 반드시 기록한다.** 이유와 함께. 그러지 않으면 반년 뒤 같은 것을 또 조사한다.
기각 사유가 "지금은 이르다"라면 언제 다시 볼지 조건을 적는다
(예: "사용자 50명 넘으면").

## 4단계 — 남기기

`docs/RADAR.md` 맨 위에 이번 주 항목을 추가한다(최신이 위). 형식:

```markdown
## 2026-09-14

**안쪽 점검** — ux-firstuse 심각 0 · privacy-scan 0 · answer-split OK · 자기검사 3/3 ✅
시나리오: 계좌 2개 동일 종목 → (결과 한 줄)

**채택**
- (제목) — 출처
  - 바뀌는 곳: (화면/함수)
  - 비용: (토큰/작업량)
  - 로드맵: (PresentationTab ROADMAP 에 넣은 항목 id)

**기각**
- (제목) — 기각 사유. 다시 볼 조건: (있으면)
```

채택 항목은 `frontend/src/tabs/PresentationTab.jsx` 의 `ROADMAP` 에 넣는다.
넣지 않으면 RADAR.md 는 읽히지 않는 일기가 된다.

지식으로 남길 값이 있으면 집현전에도 넣는다 — 다온에만 해당하는 것은 여기,
투자·자산 일반 원리는 집현전 볼트로. 판단 기준은 "다온이 없어져도 쓸모 있는가".

## 하지 말 것

- **본 것을 다 적기.** 이 문서의 가치는 거른 것에 있다.
- **출처 없이 "요즘 트렌드는" 쓰기.** URL 없으면 안 쓴 것과 같다.
- **오너 확인 없이 큰 것 착수.** 3단계까지가 이 루프의 일이고,
  구현 착수는 별개의 결정이다. 로드맵에 넣는 것까지가 여기서 하는 일이다.
- **점검 결과 미화.** 🔴 는 🔴 로 적는다. 자기검사가 죽었으면 죽었다고 적는다.

## 월 1회 회고 (매달 첫 레이더에 붙인다)

주간 루프는 "이번 주에 뭘 봤나"만 답한다. 그것만 반복하면 **채택은 쌓이는데
앱은 그대로**인 상태를 알아채지 못한다. 그래서 한 달에 한 번, 네 가지를 센다.

1. **채택 대비 착수율** — 지난 4주 채택 항목 중 실제로 구현에 들어간 것이 몇 개인가.
   0 이면 채택 기준이 헐거웠거나 상한이 여전히 높은 것이다. 상한을 3 → 2 로 내린다.
2. **사용자가 먼저 발견한 결함 수** — 오너·지인이 지적한 것 중
   내 점검이 먼저 잡을 수 있었던 것이 몇 건인가. 이 숫자가 루프의 성적표다.
   1건이라도 있으면 그 결함을 잡는 규칙을 `ux-firstuse.mjs` 에 추가하고,
   자기검사(`--selftest`)에도 그 결함을 재현해 넣는다.
3. **기각 재검토** — "다시 볼 조건"이 충족된 기각 항목이 있는가.
4. **검사기 건강** — 자기검사가 몇 주 연속 초록이었나. 규칙이 죽어도 초록은
   초록이므로, 연속 초록이 길수록 오히려 의심한다.

회고는 `docs/RADAR.md` 의 그 주 항목 아래 `**월간 회고**` 로 붙인다.
별도 파일로 빼지 않는다 — 안 읽히는 문서가 하나 더 늘 뿐이다.

### 이 루프가 실패하는 방식

미리 적어 둔다. 나중에 알아보기 위해서다.

- **채택만 하고 착수를 안 한다** → 회고 1번이 잡는다.
- **검사기가 조용히 죽는다** → `--selftest` 가 잡는다. 자기검사가 없으면 못 잡는다.
- **레이더가 조용히 멈춘다** → 이걸 잡는 장치가 아직 없다. RADAR.md 의 마지막
  날짜가 3주 이상 지났으면 세션 시작 때 알아채야 한다. (집현전 주간 종합이
  3주 동안 조용히 멈춘 적이 있다 — 같은 실패다.)
